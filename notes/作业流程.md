# 每周作业流程（按 W01 实际做法整理）

> 2026-10-24 根据 W01 实际操作整理。后续每周以当周任务书为准，本流程只作为默认做法；有冲突时听任务书的。

## 一、整体顺序

每周大致分五段，前后依赖，按顺序做：

1. **学课**：按视频顺序讲，每次带原文链接、视频编号和时间范围。
2. **跑产品**：配环境和模型，先手动试用，再跑正式验证和评估，拿到本机证据。
3. **访谈**：先写目的和提纲，再正式访谈，结束后导出记录并整理。
4. **写判断**：填 fit-gap，再写当周报告（W01 是立项报告）。
5. **检查与提交**：跑总检查，人工复核，保存快照，提交。

## 二、跑产品（在 `project/` 目录执行）

### 1. 环境与模型（只需配一次，换模型时重做）

- Python 用 3.11：`.venv` 已用 `/opt/homebrew/bin/python3.11` 建好。
- 模型配置写在 `project/.env`（已被 git 忽略）。密钥只放在这里，不发到聊天里，也不写进任何作业文件。
- 当前配置：硅基流动 + `deepseek-ai/DeepSeek-V4.1-Flash`，`FDE_MODEL_PROFILE=compatible`。
- 工程不会自动读取 `.env`，每个终端都要先执行：`set -a && source .env && set +a`。
- 换模型前先用平台的 `/models` 接口确认模型名。注意：换了模型，正式验证和评估都要用新模型重跑，证据才前后一致。

### 2. 手动试用（不算作业证据，但能发现问题）

```sh
.venv/bin/python tools/product.py start --actions --port 8775
```

本机 8765 端口被别的程序占用，所以改用 8775。按 `project/README.md` 第 2 节逐个场景试用；每个动作都到标签系统里核对真实状态，不只看页面上的说法。

### 3. 正式验证与评估（生成作业证据）

每次重跑前先备份：`cp -R artifacts/wXX ../backups/wXX-before-<步骤>-<时间>`。

```sh
.venv/bin/python tools/verify_product.py --live          # W01：11 项
cd evals && PROMPTFOO_DISABLE_TELEMETRY=1 PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 \
  npx --yes promptfoo@0.122.2 eval --config promptfooconfig.yaml --no-cache \
  --output ../artifacts/w01/promptfoo-results.json && cd ..
.venv/bin/python tools/finalize_evaluation.py
```

- Promptfoo 这一步可以交给 Codex 执行：限定只跑这一条命令，不改文件、不读 `.env`、不重试。跑完由我独立核对结果文件、模型名一致性、有无副作用和密钥泄露。
- 跑完检查证据里没有密钥：`grep -rl "$FDE_MODEL_KEY" artifacts/` 应为空。
- 有失败时按 6 类人工复核分类（protocol、data、tool、behavior、output_format、harness），不手改检查结果。

## 三、访谈

1. **访谈前**：重读客户材料，列出只有这个角色能回答的问题，按重要程度排序。每个角色每周最多 2 次，开始即扣次数，主动结束不返还。
2. **访谈中**：客户先提问时先回应；不承诺效果、时间和预算；对方答不上来就问"这个问谁比较清楚"；最后复述一遍要点，请对方确认。
3. **访谈后**：结束访谈，导出记录（JSON），原样放进 `project/docs/wXX/interviews/`，再写一份整理稿：按话题摘原话并标消息编号、证据状态初判、和产品能力的关系、待核实清单（找谁、拿什么、影响哪个判断）。

## 四、写判断

### 1. fit-gap

- W01：把空白表复制为 `artifacts/w01/product_fit_gap.xlsx`，把转换工具复制为 `tools/07_fit_gap_to_json.py`。
- W02 起：把上一版另存为 `artifacts/w02/product_fit_gap.xlsx`，沿用 GAP 编号，只改有变化的条目；在当周纪要或报告里用"适配判断更新"小节记录原判断、新判断、原因和证据位置。
- 填写方式：学员口头给判断，助手照着填，每改一次就把表格当前内容展示出来。读写 xlsx 用工程外的 `/Users/damon/code/xlsx-tools-venv`，不改作业工程的依赖。
- 转换：`.venv/bin/python tools/07_fit_gap_to_json.py`（W02 起加 `--week w02`；已有 JSON 要更新时加 `--overwrite`）。

判断时的几条分寸：

- 同一个人说多少遍，仍是"角色转述"。"已核实"要有独立来源：数据、另一个角色，或亲眼看到。
- 建立在没核实的前提上的判断，本身也没核实。
- "待判断"是现在分不了类；"暂不承诺"是清楚判断出不能承诺。两者不能互相代替。
- 一条诉求里包含几件情况不同的事，就拆成几行。
- 产品这边亲手验证过的，大胆写明已验证；客户那边的事，如实写转述或未知。

### 2. 当周报告

W01 是 `docs/w01/project_assessment.md`，按立项四问写，先写第四问的结论，再倒回去写前三问。"带条件继续"要写清：进入哪个阶段、现在先做什么、开始前缺什么、哪些情况会改变建议。

## 五、检查与提交

1. 总检查：`.venv/bin/python tools/check_product.py --root .`，按报错修正具体字段或证据。通过只说明结构没问题，内容由助教判读。
2. 人工复核：逐条看 fit-gap 和报告里的引用，确认能找到出处、没有多余承诺。
3. 保存快照：确认后用 git 提交一次，作为当周版本。
4. 提交内容：四份 JSON、当周报告、所引用的证据文件（保持路径），以及源码和依赖说明；排除 `.env`、`.venv`、`.runtime` 和无关内容。提交入口按班期配置。
5. 记录耗时：安装、运行、诊断、模型适配、文档、回归各花多久。

## 六、协作约定

- 全程用简体中文。少用表格和概念堆砌，多用具体例子。
- 讲师原文、我的解释、我补充的例子要分开标注。
- 判断和结论由学员做，助手负责准备材料、填写、核对和提醒。
- 读不到的文件要明说；"资料已收录""概念已讲过"不等于"作业已完成"。
